## Context

当前仓库已经形成一个现实上的双栈迁移局面：TypeScript 原型后端仍承接现有演示与部分生产前能力，而文档与 backlog 已经把 Python 目标栈定义为未来正式承接重型生产能力的方向。`docs/production-remediation-backlog.md` 的 `P0-03` 明确要求停止把导入、报告、PDF、邮件、异步任务等新增重型能力继续堆入 TS 原型，否则后续迁移会同时面对协议债、实现债和排期债。

这个变更主要是治理与边界设计，不是立即删除 TS 现有能力，也不是要求 Python 目标栈在本变更内完成承接。它需要给后续实现和排期一个统一规则：TS 后端只维护现有能力和必要修复，新增重型生产能力默认进入 Python 目标栈设计与 backlog。

## Goals / Non-Goals

**Goals:**
- 用正式 artifact 固化 TS 原型后端的能力边界，明确“仅维护现有能力，不再承接新增重型生产能力”。
- 定义新增重型生产能力的默认归属规则，使其统一进入 Python 目标栈设计与 backlog。
- 为研发排期、需求评审和架构讨论提供统一口径，避免后续继续将重型能力排进 TS 实现。
- 在不破坏现有 TS 演示/过渡能力的前提下，降低双栈迁移债继续扩大的风险。

**Non-Goals:**
- 在本变更中移除 TS 后端已有的导入、报告、PDF、邮件或异步任务能力。
- 在本变更中直接搭建 Python 服务或完成具体迁移实现。
- 在本变更中重新定义 DTO 单一真相，这一前置约束已由 `P0-02` 负责。
- 阻止所有 TS 代码改动；现有能力的缺陷修复、稳定性修复和必要收口仍允许继续进行。

## Decisions

### 1. 以“新增重型生产能力”而不是“所有新需求”作为冻结边界

本变更冻结的是新增重型生产能力进入 TS 原型，而不是冻结所有 TS 开发。允许继续在 TS 上做现有能力维护、问题修复、最小必要收口，但新增的导入链路、报告生产能力、PDF 正式导出、邮件投递、异步任务编排等默认不再进入 TS 主实现。

Rationale:
- 这与 backlog 对迁移债的定义一致，能直接阻断最容易放大后端复杂度的新增范围。
- 完全冻结 TS 会影响当前演示闭环和必要修复，不符合项目当前过渡阶段现实。
- 以“重型生产能力”作为边界，能让排期和评审有更可执行的判断口径。

Alternatives considered:
- 完全禁止 TS 后端任何新增改动。Rejected，因为会阻塞现有能力维护与过渡期稳定性修复。
- 只按模块冻结，不写能力判定规则。Rejected，因为实际争议通常来自“这算不算新增重型能力”，没有判定口径会继续反复讨论。

### 2. 新增重型能力默认进入 Python 目标栈设计与 backlog

当需求属于导入、报告、PDF、邮件、异步任务或同等级别的新增重型生产能力时，默认流向应是 Python 目标栈的设计、backlog 和后续实现，而不是继续放入 TS 原型后端。即使短期无法立即实现，也应先进入 Python 方向的待办，而不是为了“先做出来”再次扩大 TS 迁移债。

Rationale:
- 这把 backlog、架构方向和实施入口统一起来，避免出现“目标栈说是 Python，排期却继续进 TS”的分裂。
- 对团队来说，默认归属比逐项例外审批更容易执行。
- 这为后续 Sprint 1 / Sprint 2 的 Python 承接任务建立稳定的前置边界。

Alternatives considered:
- 允许团队按迭代压力自由选择 TS 或 Python。Rejected，因为会持续制造机会主义落点，无法真正收口迁移债。
- 为每个新能力都单独讨论技术归属。Rejected，因为治理成本高，而且会导致相同问题重复发生。

### 3. 排期与评审规则采用文档治理优先、实现治理跟进

本变更先通过 proposal/specs/tasks 建立正式治理规则，再由后续实现变更把该规则落实到 backlog、文档、评审清单或相关流程里。也就是说，第一阶段先统一“口径与准入规则”，第二阶段再把现有文档和流程对齐。

Rationale:
- 当前最紧迫的问题不是缺少一段代码，而是缺少一个被所有人共同遵循的边界定义。
- 文档治理优先可以让后续多个实现变更共享同一约束，避免每次需求都从零解释。
- 这种方式和 `P0-02` 的合同治理思路一致，适合 remediation 类变更。

Alternatives considered:
- 直接开始修改多个模块并隐含表达冻结意图。Rejected，因为没有显式规则会让后续继续误读。

### 4. 依赖 `P0-02` 作为前置协议边界，不在本变更重复定义协议真相

`P0-03` 把能力归属和实施边界收紧，但不重复定义 DTO/contract 的单一真相。所有关于前后端共享协议来源的规则继续依赖 `P0-02`，本变更只补“哪些能力还允许进 TS、哪些必须去 Python backlog”这一层。

Rationale:
- 保持 artifact 职责单一，避免两个变更都覆盖同一类治理规则。
- 让 `P0-03` 可以明确声明其依赖关系并直接承接 `P0-02` 的结果。

Alternatives considered:
- 在本变更里再次定义 contract governance。Rejected，因为会造成规范重叠和后续归档冲突。

## Risks / Trade-offs

- [“重型生产能力”定义仍可能被边缘案例挑战] -> Mitigation: 在 specs 中列出代表性范围和默认判定规则，优先按能力性质而非短期排期压力判断。
- [团队可能把“维护现有能力”误读成允许顺手扩展功能] -> Mitigation: 明确区分缺陷修复/稳定性修复与新增生产能力，并在 tasks 中要求同步到 backlog 口径。
- [Python 目标栈尚未完全就绪，可能诱发“先放 TS 顶一下”的压力] -> Mitigation: 规则上要求先进入 Python 设计与 backlog，必要时接受延后实现，但不再默认扩大 TS。
- [治理文件落地但排期文档未同步，执行会走样] -> Mitigation: 在任务中包含文档与 backlog 同步动作，确保规则不仅存在于 OpenSpec。
