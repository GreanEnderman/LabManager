## Context

当前仓库根目录已经出现多个压缩包文件和图片导出产物，同时缺少仓库级 `.gitignore`，说明“源码、依赖、构建输出、临时交付物、环境文件”之间的边界尚未冻结。这个问题虽然看起来是简单的文件治理，但它横跨前端、后端、文档、交付与本地开发环境，是一个典型的跨目录、跨流程基线问题。

本次变更的技术目标不是实现某个业务功能，而是为后续所有 P0 开发建立可持续的提交边界，让仓库默认只承载：

- 需要审查的源码与文档
- 复现构建所需的声明式配置
- 可发布流程中真正需要的模板类文件

其余内容应通过忽略规则、模板约定和交付说明被隔离出版本库。

## Goals / Non-Goals

**Goals:**
- 定义仓库级忽略规则基线，覆盖依赖目录、构建产物、缓存、日志、压缩包与常见导出图片。
- 定义环境文件分层边界，明确哪些文件可以提供模板，哪些文件必须仅保留在本地或部署环境。
- 规定“最小可交付集合”的判断标准，确保仓库保持可审查、可构建、可发布。
- 为后续新增工具链、目录或输出类型提供可扩展的治理入口，而不是一次性硬编码。

**Non-Goals:**
- 不在本次设计中引入新的 CI 平台、密钥管理产品或仓库扫描 SaaS。
- 不把所有媒体资源一刀切禁止入库；业务必需的设计资产仍可按白名单或目录约定提交。
- 不重构现有前后端构建流程本身；本次只约束构建产物的提交边界。
- 不处理历史 Git 提交清理或重写历史，这属于后续独立操作。

## Decisions

### 1. 以仓库根 `.gitignore` 作为主治理面，统一前后端与文档产物边界

本次基线以根目录 `.gitignore` 作为唯一强制入口，集中声明全仓库默认忽略规则。这样可以避免前端、后端或原型目录分别维护相互矛盾的忽略策略。

规则分层：

- 通用开发噪音：`node_modules/`、日志、缓存、临时文件、编辑器产物
- 构建与打包输出：`dist/`、`build/`、覆盖率、运行时生成目录
- 交付压缩物：`*.zip`、`*.tar`、`*.gz`、`*.7z`
- 导出型图片产物：例如 `mermaid-diagram-*.png` 等流程图/截图导出结果
- 环境文件：`.env` 及其本地变体，但保留模板命名策略

Rationale:
- 单一入口更容易评审和维护。
- 当前问题出现在仓库根层面，根规则更能覆盖已有噪音文件类型。

Alternatives considered:
- 让每个子项目维护自己的 `.gitignore`。Rejected，因为跨目录产物如压缩包和导出图片仍然会泄漏到仓库根。
- 只依赖全局 Git ignore。Rejected，因为它不可审查，也无法成为团队共享规则。

### 2. 环境文件采用“模板可入库，真实值不入库”的双层策略

环境文件治理采用以下约束：

- `.env`、`.env.local`、`.env.development.local`、`.env.production.local` 等真实环境文件默认不入库
- `.env.example`、`.env.template` 等不含敏感值的模板文件允许入库
- 若某个模块需要示例配置，必须通过模板文件或文档说明表达，而不是提交真实配置副本

Rationale:
- 这符合“可构建”与“不可泄漏”之间的平衡。
- 能让新成员或部署流程知道需要哪些变量，同时不暴露实际密钥。

Alternatives considered:
- 完全禁止任何环境相关文件入库。Rejected，因为会损害可启动性与交付清晰度。
- 允许提交开发默认值 `.env`。Rejected，因为边界会迅速退化，并可能误提交敏感信息。

### 3. 构建产物默认不入库，只有源码资产和显式模板可以留在仓库

仓库中的 `dist`、`build`、覆盖率报告、打包目录、缓存快照等全部视为派生产物，不作为交付源代码的一部分。业务上需要被版本控制的静态资产，必须满足“源资产”属性，例如设计稿原文件、应用图标、产品文档插图，而不是由工具临时导出的结果。

这意味着：

- `dist/`、`build/`、`.vite/`、缓存目录一律忽略
- 自动导出的图片产物按命名模式或目录规则忽略
- 若图片是产品正式素材，应放入明确的源资产目录，并通过命名/文档说明其用途

Rationale:
- 可以把仓库交付面收敛回“可审查的源文件”。
- 避免评审和 diff 被机器生成文件淹没。

Alternatives considered:
- 将部分构建产物保留用于演示。Rejected，因为演示交付应通过发布包或文档流程提供，不应污染主仓库。

### 4. 最小可交付集合用“可审查、可构建、可发布”三段式判断

仓库内容是否应被提交，采用统一判断：

- 可审查：人类评审能从 diff 中获得稳定价值
- 可构建：构建所需输入文件齐备，但不包含构建结果
- 可发布：发布流程可从仓库产出交付物，但仓库本身不等同于交付包

不满足上述标准的文件类型应通过忽略规则排除，或改为模板、文档、脚本化生成。

Rationale:
- 这比单纯罗列文件后缀更稳定，适合作为后续扩展原则。

Alternatives considered:
- 仅通过扩充后缀黑名单治理。Rejected，因为新工具链出现时很容易漏掉。

## Risks / Trade-offs

- [忽略规则过宽，误伤业务必需素材] → Mitigation: 对“源资产目录”使用明确白名单约定，并在实施时先检查现有真实素材位置。
- [只定义规则但未同步文档，团队仍可能误提交] → Mitigation: 在任务中要求补充仓库交付策略说明。
- [环境模板命名不统一，后续子项目仍会各自演化] → Mitigation: 在实施中统一模板命名和示例说明格式。
- [历史噪音文件已存在，短期内会让仓库看起来仍然杂乱] → Mitigation: 将“清理已入库产物”和“建立未来防线”拆分，先完成规则与基线，再执行清理。

## Migration Plan

1. 盘点当前仓库中的依赖目录、构建目录、压缩包、导出图片与环境文件现状。
2. 新增或收敛根目录 `.gitignore`，按通用噪音、构建产物、交付压缩物、导出图片、环境文件进行分段治理。
3. 如缺少模板类环境文件约定，补充 `.env.example` 或对应说明文档。
4. 在文档中记录提交策略与交付边界，明确哪些内容不应进入版本库。
5. 复查 Git 状态，确认仓库交付面已收敛到最小可审查集合。

Rollback strategy:

- 若某条忽略规则误伤必要文件，可通过更精确的白名单例外修正，而不是整体撤回基线。
- 回滚应仅调整规则与文档，不重新放宽“真实环境文件和派生产物可入库”的原则。
