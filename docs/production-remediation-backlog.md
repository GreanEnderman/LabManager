# LabManager 生产级整改任务清单

## 1. 文档目的

本文档基于以下现状共同整理：

- 当前代码实现状态
- `docs/stack-migration-roadmap.md`
- `docs/project-sync-status.md`

目标不是继续扩写功能愿景，而是把当前仓库从“可演示 / 原型可跑”收敛到“可进入生产迁移准备”的执行清单。

本文默认遵循以下判断：

- 当前仓库已明显超出“仅 TS 领域原型”的早期阶段
- TS 后端已经承接了任务、审批、规则、导入、报告、PDF、邮件投递、HTTP API 等多项生产前能力
- 生产整改重点不再是补几个页面，而是收口运行主链路、协议真相、数据真相、迁移边界和交付基线

## 2. 执行分层

任务按四层组织：

1. `P0 生产阻塞`
2. `Sprint 1（两周内）`
3. `Sprint 2（迁移启动）`
4. `迁移期守则`

## 3. P0 生产阻塞

### P0-01 统一生产运行主链路

- 目标：明确生产环境前端只走 HTTP gateway，停止把旧 `AIContext` mock 状态层当成真实运行路径。
- 验收标准：
  - 生产 / 预发环境固定使用 `VITE_AI_GATEWAY_MODE=http`
  - `frontend/src/ai/AIContext.tsx` 和同类 mock 状态层被明确标注为演示专用
  - 后续新功能不再接入旧 mock AI 状态层
- 依赖关系：无

### P0-02 冻结共享 DTO 为唯一真相

- 目标：以后端共享 contracts 作为前后端与双栈迁移的唯一协议源。
- 验收标准：
  - `backend/src/contracts/shared.ts` 被明确指定为唯一 DTO 源
  - 前端消费 DTO 的映射规则有文档约束
  - 新接口不再定义平行字段语义
- 依赖关系：`P0-01`

### P0-03 停止 TS 原型继续承接新增重型能力

- 目标：防止导入、报告、PDF、邮件、异步任务继续在 TS 原型中扩大迁移债。
- 验收标准：
  - 形成书面边界：TS 后端仅维护现有能力，不再承接新增重型生产能力
  - 新增生产能力默认进入 Python 目标栈设计与 backlog
  - 研发排期不再把新增重型能力放入 TS 实现
- 依赖关系：`P0-02`

#### P0-03 执行边界

- `maintenance-only TS backend` 定义：
  - 允许：现有 TypeScript 后端能力的缺陷修复、稳定性修复、必要的兼容性收口、迁移期只读/对照支撑
  - 不允许：新增导入链路、报告生成扩展、正式 PDF 能力、生产邮件投递、异步任务编排、同等级别的新重型后端能力
- `new heavy production capability` 默认判定：
  - 只要新增需求主要增加后端工作流责任、批处理/异步处理、文件/PDF/邮件投递、导入导出编排、生产级任务调度，即默认按新增重型生产能力处理
  - 边缘需求若无法明确归类，评审时默认按“新增重型生产能力”收口，除非能明确缩回现有能力维护范围
- 评审与排期规则：
  - 需求评审、技术方案评审、backlog grooming、迭代排期时，必须先判断是“现有能力维护”还是“新增重型生产能力”
  - 一旦被判定为新增重型生产能力，默认进入 Python 目标栈设计与 backlog，而不是继续排入 TS 实现
  - 不允许以“先在 TS 顶一下”为默认捷径；如 Python 目标栈尚未准备好，可延后实现，但不改变能力归属

### P0-04 修复生产配置与默认凭据风险

- 目标：清除默认账号、默认密码、默认密钥导致的生产阻塞。
- 验收标准：
  - 默认管理员账号和默认密码策略被移除或禁用
  - JWT secret、SMTP、LLM 等敏感配置全部外部注入
  - 本地、测试、预发、生产环境的配置边界被定义清楚
- 依赖关系：无

### P0-05 定义正式持久化模型

- 目标：把当前快照式 Postgres 持久化从“过渡原型”收口为正式数据模型迁移目标。
- 验收标准：
  - 明确 `ai_tasks`、`ai_task_actions`、`approvals`、`ai_reports`、`import_jobs`、`report_deliveries`、`system_settings` 等正式表模型
  - 明确主键、索引、外键、审计字段与 `metadata` 约定
  - 明确 snapshot store 仅为过渡方案，不作为生产真持久化
- 依赖关系：`P0-02`

### P0-06 建立仓库与交付卫生基线

- 目标：解决缺少忽略规则、构建产物混入仓库、压缩包与环境文件边界不清的问题。
- 验收标准：
  - 明确 `.gitignore` 规则
  - 明确 `dist`、`node_modules`、zip、图片产物、环境文件的提交策略
  - 仓库交付面收敛到可审查、可构建、可发布的最小集合
- 依赖关系：无

### P0-07 同步当前实现与目标架构文档

- 目标：消除“当前已实现能力”和“目标生产栈规划”混写造成的误判。
- 验收标准：
  - 文档明确区分当前实现栈、TS 原型边界、Python 目标栈、迁移窗口
  - 团队默认参考顺序被固定
  - 历史方向性文档不再被误当作当前真实状态
- 依赖关系：可与其他 P0 项并行

## 4. Sprint 1（两周内）

### S1-01 搭建 Python 主后端基础骨架

- 目标：建立 FastAPI、PostgreSQL、Redis、Celery、LangGraph Python 的最小可运行工程。
- 验收标准：
  - Python 服务骨架可启动
  - 健康检查、配置加载、基本目录结构、任务队列骨架具备
  - 与当前仓库结构的协作边界清晰
- 依赖关系：`P0-04`、`P0-05`

### S1-02 设计首批迁移能力边界

- 目标：把规则服务、导入服务、报告生成、PDF、邮件投递、异步任务列为 Python 首批承接能力。
- 验收标准：
  - 每项能力都具备输入输出契约
  - 明确与 TS 现有实现的对照关系
  - 明确迁移顺序、切流顺序、回退策略
- 依赖关系：`S1-01`、`P0-02`

### S1-03 建立正式数据库 schema 与迁移机制

- 目标：从内存仓储和 snapshot 持久化过渡到正式关系模型。
- 验收标准：
  - 关键业务表具备正式 schema
  - 存在迁移脚本机制
  - 模型可支撑任务、审批、导入、报告、投递、配置和审计
- 依赖关系：`P0-05`、`S1-01`

### S1-04 提升认证鉴权到生产基线

- 目标：把当前演示级登录和角色判断提升到生产可控水平。
- 验收标准：
  - 角色矩阵定义清楚
  - token 生命周期与认证失效策略明确
  - 密码策略、默认账户禁用策略、鉴权失败响应规范齐备
- 依赖关系：`P0-04`

### S1-05 统一前端真实联调模式

- 目标：让测试与预发环境只验证 HTTP 后端，不再混入 direct/mock 路径。
- 验收标准：
  - 联调环境默认走 `/api/ai`
  - 运行模式切换规则有说明
  - 页面不会在联调时悄悄退回 mock 逻辑
- 依赖关系：`P0-01`、`S1-04`

### S1-06 建立 API 级回归和权限测试基线

- 目标：从当前脚本验证扩展到面向迁移的契约测试与权限测试。
- 验收标准：
  - 覆盖任务、审批、导入、报告、投递、权限边界、失败分支
  - 测试结果可作为双栈迁移前后对照基线
  - 关键链路失败时能定位到接口或权限层
- 依赖关系：`P0-02`、`S1-04`

### S1-07 产品化外部依赖配置

- 目标：把 PDF 字体、LLM、SMTP 等依赖从“本机可跑”提升为“环境可部署”。
- 验收标准：
  - PDF 字体策略不再依赖固定 Windows 路径
  - SMTP 和 LLM 有环境配置说明
  - 失败时的降级、告警或兜底策略被定义
- 依赖关系：`P0-04`、`S1-01`

## 5. Sprint 2（迁移启动）

### S2-01 Python 承接规则服务

- 目标：先迁最核心但边界清晰的规则识别与巡检能力。
- 验收标准：
  - 三类事件识别与判重在 Python 可运行
  - 与 TS 参考实现输出可对照
  - 规则输入输出协议保持一致
- 依赖关系：`S1-02`、`S1-03`

### S2-02 Python 承接导入服务

- 目标：将在线导入、校验、批次追溯迁入目标栈。
- 验收标准：
  - 支持手工录入与批量导入
  - 返回错误清单与批次历史
  - 导入后可联动规则检查
- 依赖关系：`S2-01`、`S1-03`

### S2-03 Python 承接报告生成与 PDF 导出

- 目标：把报告生成和正式 PDF 能力迁入目标栈。
- 验收标准：
  - 日报、周报等报告生成能力可运行
  - PDF 导出接口稳定
  - 字体、版式和部署环境约束被解决
- 依赖关系：`S1-01`、`S1-07`

### S2-04 Python 承接邮件投递与异步任务

- 目标：将报告发送、失败处理、后台任务从 TS 原型抽离。
- 验收标准：
  - 手动发送可用
  - 发送记录、失败重试、后台任务链路具备
  - 投递能力不再依赖 TS 原型主实现
- 依赖关系：`S2-03`、`S1-07`

### S2-05 建立 TS / Python 双轨对照回归

- 目标：确保迁移不是“重写后感觉差不多”，而是关键行为对齐。
- 验收标准：
  - 相同输入在关键链路上可对照输出
  - 行为差异有记录和裁决结果
  - 可作为阶段性切流前的准入检查
- 依赖关系：`S1-06`、`S2-01`、`S2-02`、`S2-03`、`S2-04`

## 6. 迁移期守则

### M-01 前端单 DTO 守则

- 目标：避免前端同时依赖两套字段语义。
- 验收标准：
  - 前端只消费一套统一 DTO
  - 适配逻辑集中在 gateway / facade 层
  - 页面层不出现双协议并存分支
- 依赖关系：`P0-02`

### M-02 TS 原型后端冻结守则

- 目标：让 TS 后端只做参考实现、对照回归和未切流量承接。
- 验收标准：
  - 不再向 TS 原型新增业务语义
  - 所有新增重型能力默认进入 Python backlog
  - TS 后端定位在团队内有统一口径
- 依赖关系：`P0-03`

- 守则说明：
  - TS 原型后端仍可承担当前已落地能力的维护，但不再作为新增重型生产能力的主实现归属
  - Python 目标栈是导入、报告、PDF、邮件、异步任务及同等级重型能力的默认承接方
  - backlog、设计文档、排期说明若涉及以上能力，应明确标注为 Python intake，而不是 TS 扩展

### M-03 审计连续性守则

- 目标：保证任务、审批、导入、报告、投递、Agent runId 在迁移过程中不断档。
- 验收标准：
  - 跨栈可追踪操作者、原因、结果、时间和 runId
  - 审计字段语义在迁移前后保持一致
  - 双轨阶段可以对账
- 依赖关系：`S1-03`、`S1-06`

### M-04 分阶段切流守则

- 目标：按能力切换，而不是一次性整体切换。
- 验收标准：
  - 先切规则、导入、报告、PDF、邮件、异步任务
  - 再切任务 API、审批 API、活动日志主 API
  - 每阶段都有回退方案
- 依赖关系：`S2-05`

### M-05 TS 下线前置条件守则

- 目标：防止过早删除 TS 参考后端。
- 验收标准：
  - Python 主 API 稳定
  - 前端已完成主路径切换
  - 回归通过，审计连续
  - 满足以上条件后才允许逐步下线 TS API
- 依赖关系：`M-04`

## 7. 建议执行顺序

推荐实际推进顺序如下：

1. 先完成全部 `P0 生产阻塞`
2. 再推进 `Sprint 1（两周内）`
3. 然后启动 `Sprint 2（迁移启动）`
4. 全程遵守 `迁移期守则`

## 8. 一句话结论

对当前仓库而言，最重要的不是“现在立刻整体切栈”，也不是“继续在 TS 原型里补齐全部生产能力”，而是先把生产真相、协议真相、持久化真相和迁移边界收口，再按增量双轨方式把重型后端能力迁到 Python 目标栈。
